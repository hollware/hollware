# Hollware starter

The project template behind `npm create hollware`, which arrives with v0.4. It is the thin
project a user gets: a config, a Worker that builds itself from it, and the Wrangler config that
binds the database. It builds, type-checks and tests with the same tools Hollware's own packages
use, and the Worker it builds is the one Hollware's size budget measures.

## What is inside

| Path                        | What it is                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `hollware.config.ts`        | Your config: one site, `my-site`, with a small bilingual blog (English and Spanish)             |
| `src/worker.ts`             | The Worker. `createHollware(config)` gives its `fetch` and the `Hollware` class sites read from |
| `wrangler.jsonc`            | The Worker `my-hollware`: D1 `DB`, KV `OAUTH_KV` and its public URL `HOLLWARE_PUBLIC_URL`       |
| `vite.config.ts`            | Vite with `@cloudflare/vite-plugin`, minified                                                   |
| `vitest.config.ts`, `test/` | Tests that run inside workerd through `@cloudflare/vitest-plugin`                               |
| `worker-configuration.d.ts` | Generated by `wrangler types`. Commit it, and refresh it whenever `wrangler.jsonc` changes      |

The D1 binding reads its migrations from `node_modules/@hollware/server/migrations`, the
directory the server package ships. Its `database_id` is a placeholder that works for local
development; put the id of your own database there before deploying.

`OAUTH_KV` holds what the OAuth server issues: the clients that sign in, their grants and their
tokens, all by hash. MCP clients that speak OAuth, such as claude.ai, connect through it once a
person signs in with a passkey and allows them. Its `id` is a placeholder too: create the namespace
with `pnpm exec wrangler kv namespace create OAUTH_KV` and put its id there before deploying.
Agents that use a personal token do not need it.

`HOLLWARE_PUBLIC_URL` is the only Host and Origin the Worker answers, and any other request is
refused. It is `http://localhost:5199`, the URL `pnpm dev` serves; set it to the public URL of
the Worker before you deploy.

The Worker runs without Node.js compatibility: `wrangler.jsonc` lists `no_nodejs_compat` and
`no_nodejs_compat_v2`, because Workers turn it on by default from the 2026-08-04 compatibility
date. Remove both flags only if your own code needs Node.js APIs. It also lists
`global_fetch_strictly_public`, so that the OAuth server fetches the metadata documents of clients
over the public internet only; keep it. Wrangler's anonymous telemetry
is yours to decide: this template sets nothing for it.

## Run it

```sh
pnpm install
pnpm exec wrangler d1 migrations apply DB --local   # the tables, in the local database
pnpm dev                                            # http://localhost:5199
```

An agent needs a personal token to write over MCP at `/mcp`. The `hollware` command-line
package creates the site, its owner and the first token in one step, and prints the token once:
`hollware init --site my-site --local`.

A site on the same account reads what you publish over a service binding, with no network and
no token. `examples/worker-site` in the Hollware repository is one: a blog that binds this
Worker by its name and its `Hollware` entrypoint.

## Commands

| Command            | What it does                                         |
| ------------------ | ---------------------------------------------------- |
| `pnpm dev`         | Serve the Worker locally with Vite                   |
| `pnpm build`       | Build the Worker into `dist/`                        |
| `pnpm test`        | Run the tests in workerd                             |
| `pnpm types`       | Regenerate `worker-configuration.d.ts`               |
| `pnpm types:check` | Fail when `worker-configuration.d.ts` is out of date |
